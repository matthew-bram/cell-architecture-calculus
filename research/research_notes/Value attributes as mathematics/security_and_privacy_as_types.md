# Security and privacy as types and theorems

Research notes, compiled 2026-10-14. Every finding is tagged with how it was obtained:
**[source]** = read directly in the primary document (verbatim or near-verbatim);
**[summary]** = read through a fetch-tool summary of the primary document, or in a secondary page (abstract, README, encyclopedia);
**[memory]** = from the researcher's prior knowledge, not re-verified this session. Treat [memory] items as leads to check, not as citations.

The reader's model: identifiers indexed by a trust zone (`Id z`), so a record in zone A built from an `Id B` is a type error; a single `scrub` function whose type names two zones; commands carry an actor that a policy checks before a decision. The notes answer, per question, what this is called, what theorem it corresponds to, and what is mechanized.

## Q0. What the reader's construction is called, and which theorem it corresponds to

### Takeaway
The zone-indexed identifier is the *security-typed data* / "labels as type indices" pattern of the information-flow-control (IFC) literature (Denning's lattice turned into a type system by Volpano–Smith–Irvine, encoded with phantom or dependent types in SecLib, MAC, DepSec, and Lourenço–Caires). The theorem it corresponds to is **noninterference** (a 2-safety hyperproperty). The `scrub` function is a **declassification** at a fixed *where* (the single escape hatch) whose *what* is governed by **delimited release**; the actor on the command is the **who** dimension (robust declassification / integrity), and the policy check before the decision is a **reference monitor** satisfying **complete mediation**, whose correctness statement has the same shape as Cedar's Lean theorems ("explicit permit required", "default deny").

### Cited Findings
- Denning (CACM 1976) gave "a mathematical framework suitable for formulating the requirements of secure information flow among security classes," with a lattice of security classes as the central structure; it unifies systems that restrict information flow including Bell–LaPadula and Biba. [summary] — [ACM DL](https://dl.acm.org/doi/10.1145/360051.360056)
- Volpano, Smith and Irvine (JCS 1996) "formulated Denning's approach as a type system and presented a notion of soundness for the system that can be viewed as a form of noninterference"; "soundness was established by proving, with respect to a standard programming language semantics, that all well-typed programs have the noninterference property." [summary] — [SAGE / JCS](https://journals.sagepub.com/doi/10.3233/JCS-1996-42-304); [ACM DL](https://dl.acm.org/doi/10.5555/353629.353648)
- Sabelfeld and Myers (IEEE JSAC 2003) state noninterference as: if two inputs are indistinguishable to a low observer then the corresponding outputs are indistinguishable; the assignment rule carries a program-counter label `pc` to block implicit flows; Jif and Flow Caml are the practical security-typed languages; integrity is the dual of confidentiality on the reversed lattice; noninterference alone "cannot express intentional, controlled releases," hence declassification. [summary] — [sm-jsac03.pdf](https://www.cs.cornell.edu/andru/papers/jsac/sm-jsac03.pdf)
- Lourenço and Caires (POPL 2015) introduce *dependent information flow types* that "fit within the standard framework of dependent type theory" but let "the security level of a type depend on runtime values," with "type-safety and non-interference theorems ensuring that well-typed programs do not violate prescribed security policies." [summary] — [POPL 2015 paper](https://dl.acm.org/doi/pdf/10.1145/2775051.2676994)
- MAC (Vassena, Russo et al.) is a statically enforced IFC library for Haskell; the formalization in a call-by-need calculus proves progress-insensitive noninterference, and the full Agda development (exceptions, references, concurrency) proves "a scheduler-parametric, progress-sensitive non-interference theorem." [summary] — [ScienceDirect (JLAMP)](https://www.sciencedirect.com/science/article/pii/S235222081730069X); [agda-mac repo](https://github.com/marco-vassena/agda-mac)
- DepSec (Gregersen, Thomsen, Askarov, POST 2019) is "a MAC inspired, dependently typed library for static information-flow control in Idris," showing that dependent types "increase the expressiveness of state-of-the-art static IFC libraries" and give "novel and powerful means of specifying statically enforced declassification policies." [summary] — [full paper](https://cs.au.dk/~gregersen/papers/2019-post-depsec-full.pdf); [repo](https://github.com/simongregersen/DepSec)
- Bowman and Ahmed, "Noninterference for Free" (ICFP 2015): DCC's noninterference "suggests a connection to parametricity in System F"; they translate DCC into Fω and prove the translation preserves noninterference. [summary] — [nifree.pdf](http://www.ccs.neu.edu/home/amal/papers/nifree.pdf); Algehed and Bernardy, "Simple Noninterference from Parametricity" (ICFP 2019) [summary, title only] — [ACM DL](https://dl.acm.org/doi/pdf/10.1145/3341693)
- Clarkson and Schneider: "Noninterference is not a trace property but rather a 2-safety hyperproperty." [summary] — [Hyperproperties (CSF 2008 version)](https://www.cs.cornell.edu/fbs/publications/HyperpropertiesCSFW.pdf)
- Anderson (1972) described the reference monitor, "a guard that checks every access to every object, cannot be tampered with, and is small enough to verify"; Saltzer and Schroeder (1975) named *complete mediation*: "every access to every resource is checked for authority, every time." [summary] — [Schneider, Reference Monitors chapter](https://www.cs.cornell.edu/fbs/publications/chptr.enfMech.refMonitor.pdf); [Wikipedia: Protection of Information in Computer Systems](https://en.wikipedia.org/wiki/The_Protection_of_Information_in_Computer_Systems)

### Inferences
- Name for the identifier-indexing: in Denning's vocabulary the zones are *security classes*; in the reader's design the classes are pairwise *incomparable* (no zone flows to another), so the lattice is an antichain plus the implicit top/bottom, and the policy is "no flow between zones except through scrub." In type-system vocabulary this is a *label-indexed type family* (`Labeled l a` in MAC, `Id z` here). The type-formation rule that refuses `Record A` built from `Id B` is the dependent-type analogue of VSI's "no assignment from a higher class to a lower variable."
- The theorem the reader is "getting for free" is of the form *well-typed ⇒ noninterferent*: for every two states that agree on everything observable from zone A (differ only in zone B data), every well-typed computation yields states that still agree on zone A observables. This is a *meta*-theorem about the host type system, obtained in the literature by logical relations or parametricity. Lean 4 does not expose internal parametricity (it has classical choice and large elimination [memory]), so the reader cannot *prove inside Lean* that Lean's checker enforces noninterference on the model merely because the indices are there; the honest statement is that the index makes the forbidden term *unwritable*, and a separate two-run theorem over an explicit semantics of the model's commands is what would make noninterference a Lean theorem.
- The `scrub` function occupies exactly the slot of MAC/DepSec's privileged declassification combinator and VSI/Jif's `declassify`: the one typing rule that relates two labels.
- The policy-before-decision check is a reference monitor. If `Decision` can only be constructed from evidence `Policy.allows actor cmd`, then "every decision was authorized" is correct by construction — the same shape as Cedar's "explicit permit required."

### Gaps
- I did not find a paper that names the exact combination "incomparable zones + a single two-zone function" as a pattern; it is assembled from Denning (lattice), delimited release (single hatch) and NMIF (who).

## Q1. Information-flow type systems and the noninterference theorem; "noninterference by typing" with indexed types; mechanizations

### Takeaway
The noninterference theorem says: two runs from low-equivalent inputs produce low-equivalent outputs; VSI 1996 proved all well-typed programs satisfy it (termination-insensitively). Indexing data by a level makes the type checker refuse the flows the lattice forbids, and the theorem is then proven once about the type system, usually by a logical relation or parametricity. Mechanizations exist in Agda (MAC), Coq/Rocq+Iris (Gregersen et al. POPL 2021), and Coq (DCC in CoC); for Lean 4 I found only self-published and very recent (mid-2026) items and no established library.

### Cited Findings
- Noninterference theorem shape (VSI 1996, restated by Smith): for a simple while-language where each variable has a class from a lattice, if `γ ⊢ c : τ cmd` and memories μ, ν agree on all variables of class ≤ L, and both runs terminate in μ′, ν′, then μ′ and ν′ agree on all variables of class ≤ L. The `τ cmd` judgment means c assigns only to variables of class ≥ τ, which is how `pc` blocks implicit flows through `if`/`while`. [memory; the Smith chapter PDF did not parse this session] — [Smith, Principles of Secure Information Flow Analysis](https://www.cs.cornell.edu/courses/cs5430/2013sp/paper.smithInfoFlow.pdf)
- Termination-insensitive vs termination-sensitive: the JSAC survey distinguishes NI that ignores termination/timing behaviour from variants that account for it. [summary] — [sm-jsac03.pdf](https://www.cs.cornell.edu/andru/papers/jsac/sm-jsac03.pdf)
- Abadi, Banerjee, Heintze, Riecke, "A Core Calculus of Dependency" (POPL 1999): DCC with a monad `T_l` per lattice element; its denotational semantics "formalizes the notion of noninterference." [summary] — [abadi99core.pdf](https://www.cs.cornell.edu/andru/cs711/2003fa/reading/abadi99core.pdf)
- Phantom-type encodings in Haskell: Li and Zdancewic, "Encoding information flow in Haskell" (CSFW 2006); Russo, Claessen and Hughes, "A library for light-weight information-flow security in Haskell" (Haskell 2008, SecLib). [memory for titles/venues; the latter confirmed by a search hit] — [ResearchGate listing](https://www.researchgate.net/publication/311463406_A_library_for_light-weight_information-flow_security_in_haskell)
- Gregersen, Bay, Timany, Birkedal (POPL 2021): an IFC type system with recursive, existential, label-polymorphic and impredicative polymorphic types for a higher-order language with higher-order state; "a novel semantic model showing that well-typed programs satisfy termination-insensitive noninterference"; mechanized in Coq/Rocq on Iris; supports mixing well-typed and ill-typed-but-semantically-sound components. [summary] — [Aarhus listing](https://pure.au.dk/portal/en/publications/mechanized-logical-relations-for-termination-insensitive-noninter/); DOI 10.1145/3434291
- Rajani and Garg: "a step-indexed Kripke-style logical-relations model for two information-flow control type systems for a sequential language with higher-order state," used to prove the fine-grained and coarse-grained static IFC systems equivalent. [summary] — search summary; paper is "Types for Information Flow Control: Labeling Granularity and Semantic Models" (CSF 2018) [memory for title/venue]
- Noninterference for a polyvariant DCC proved in the Calculus of Constructions, "modular and leverages parametricity for the Calculus of Constructions." [summary] — [LMCS: Proving Noninterference by a Fully Complete Translation to the Simply Typed lambda-calculus](https://lmcs.episciences.org/683) (Tse and Zdancewic / Shikuma and Igarashi line [memory])
- Nanevski, Banerjee, Garg (TOPLAS 2013), Relational Hoare Type Theory: "a number of security policies which have been formalized separately in the literature can all be expressed in RHTT using only standard type-theoretic constructions such as monads, higher-order functions, abstract types, abstract predicates, and modules," including conditional declassification, erasure, and state-dependent flow and access control. [summary] — [toplas13.pdf](https://people.mpi-sws.org/~dg/papers/toplas13.pdf)
- Lean 4 items found: (a) **Sigil** (GitHub, nxrobins), self-described as "a capability-safe language with effects, taint labels, and linear ownership ... a mechanized Lean soundness development," with "noninterference machine-checked in Lean 4" — a self-published repository, not a peer-reviewed result. [summary] — [nxrobins/sigil](https://github.com/nxrobins/sigil). (b) Gouni, Pfenning, Aldrich, "The Duality of Information Flow: Reconciling Robust Downgrading with Non-Interference" (arXiv, July 2026): open/closed modalities unify confidentiality and integrity; noninterference "through a binary logical relations argument"; "robustness as an ordinary 2-hyperproperty mediated by our modalities." The abstract did not state the proof assistant; a search summary claimed Lean. [summary; mechanization unverified] — [arXiv 2607.17445](https://arxiv.org/abs/2607.17445). (c) Barthe, "Formalization of security" (arXiv, July 2026), a book chapter surveying proof-assistant formalizations of "system security, language-based security, secure compilation, and cryptography." [summary] — [arXiv 2607.28551](https://arxiv.org/abs/2607.28551). (d) "Iris in Lean" (de Medeiros, Jung, Carneiro, Tassarotti, Sammler, Birkedal et al., arXiv Sept 2026): Iris reimplemented in Lean with the proof mode, quotient types for equivalences, and Mathlib integration, demonstrated on probabilistic program verification. [summary] — [arXiv 2609.24252](https://arxiv.org/abs/2609.24252)

### Inferences
- "Noninterference by typing" in a dependent type system works in two layers: (1) the index makes the ill-typed flow *unwritable* (what the reader has); (2) a theorem *about* the typed language shows every writable program is noninterferent (what MAC proves in Agda, DepSec inherits from MAC's argument, and Gregersen et al. prove in Iris). The reader's model currently has layer 1 only.
- The practical Lean route to layer 2 is the one Gregersen et al. and Gouni et al. use: a binary (two-run) logical relation over an explicit operational semantics of the model's commands. "Iris in Lean" (Sept 2026) makes this feasible in Lean 4 with Mathlib available, which it was not a year earlier.

## Q2. Declassification: dimensions, the single trusted function, and the property it must satisfy

### Takeaway
Sabelfeld and Sands classify declassification by *what/who/where/when* and give four prudent principles; a single, fixed `scrub` is a *where* (code locality) declassification whose released information should be stated with *delimited release* (the scrub's outputs are the only escape hatches); because commands carry an actor, the *who* dimension applies as *robust declassification*, and the modern combined statement (robust declassification + transparent endorsement) is nonmalleable information flow, a 4-safety hyperproperty.

### Cited Findings
- Sabelfeld and Sands "classify basic declassification goals according to four axes: *what* information is released, *who* releases information, *where* in the system information is released and *when* information can be released." [summary] — [sabelfeld-sands-jcs07.pdf](https://www.cse.chalmers.se/~andrei/sabelfeld-sands-jcs07.pdf)
- Delimited release: the policy "is expressed in terms of a collection of escape hatch expressions which are marked within the program via a declassify annotation," and "stipulates that information may only be released through escape hatches and no additional information is leaked." [summary] — same source
- Formal shape of delimited release (Sabelfeld and Myers, ISSS 2003): a program c with hatches e₁..eₙ is secure iff for all memories M₁ =_L M₂ with eᵢ(M₁) = eᵢ(M₂) for all i, the low-observable results of running c on M₁ and M₂ are equal; i.e. the attacker learns at most the hatch values. [memory]
- Prudent principles: *semantic consistency*, *conservativity* ("security conservatively extends the notion of security for a language without declassification"), *monotonicity of release*, and *non-occlusion* ("the presence of declassifications cannot mask other covert information leaks"). [summary] — same source
- Robust declassification (the who dimension): "attackers cannot selectively trigger declassification of chosen secrets through their inputs" — the attacker cannot influence what is declassified. [summary] — same source; original is Zdancewic and Myers, CSFW 2001 [memory]
- Localized delimited release (Askarov and Sabelfeld, PLAS 2007) adds the *where* to delimited release: a hatch releases only after the program reaches its declassification point. [summary, title] — [askarov-sabelfeld-plas07.pdf](https://www.cse.chalmers.se/~andrei/askarov-sabelfeld-plas07.pdf)
- Relaxed noninterference (Li and Zdancewic, POPL 2005): labels are sets of downgrading policies (functions) saying which functions of a secret may be released. [memory]
- Nonmalleable information flow (Cecchetti, Myers, Arden, CCS 2017): combines robust declassification ("declassification decisions cannot be manipulated by an attacker's inputs") with its dual, transparent endorsement (secret data cannot be endorsed to high integrity); labels are (confidentiality, integrity) pairs; NMIF "qualifies as a 4-safety hyperproperty." [summary] — [arXiv 1708.08596](https://arxiv.org/pdf/1708.08596)
- Cryptographically masked flows (Askarov, Hedin, Sabelfeld, SAS 2006): encryption treated as a declassification with a possibilistic noninterference condition that ignores ciphertext values. [memory]
- DepSec expresses declassification policies with dependent types (e.g., release only aggregates, or only after a predicate holds). [summary] — [DepSec paper](https://cs.au.dk/~gregersen/papers/2019-post-depsec-full.pdf)

### Inferences
- The reader's `scrub` is the single escape hatch; the property to *state* about it is delimited release with `scrub` as the only hatch: for any two private zone states that agree on everything outside the private zone and on `scrub`'s output, the outside world cannot distinguish them. The property to state about `scrub` *itself* is separate: that the pseudonym carries no information about the identity without the key held in the private zone (the cryptographically-masked-flows condition).
- Because the actor is on the command, robust declassification is the relevant *who* condition: an actor who is not trusted by the private zone must not be able to influence *which* record is scrubbed or *when*; in NMIF terms the `pc` at the scrub call must have private zone integrity, which is what "policy checks the actor before a decision is made" supplies if the decision guards the scrub.
- The non-occlusion principle is the test for the design: adding `scrub` must not hide another channel (e.g., the identifier's equality being observable across zones, or an error message that mentions the other zone's id).

### Gaps
- The exact formula of delimited release and the Zdancewic–Myers robust-declassification definition were not read in the originals this session.

## Q3. Hyperproperties: why confidentiality is 2-safety and what that means for recorded runs versus models

### Takeaway
Clarkson and Schneider define a hyperproperty as a set of sets of traces; noninterference is 2-safety, so no single recorded run can violate it, and no single-run assertion can state it. It can be checked on a *pair* of runs (self-composition / product programs) and proven on a model; refinement does not preserve it. Differential privacy is a relational (hyper)property of output *distributions*, not a k-safety property on traces.

### Cited Findings
- "A hyperproperty is a set of sets of traces"; "a property is k-safe if violations can be detected by observing k traces"; "noninterference is not a trace property but rather a 2-safety hyperproperty." [summary] — [HyperpropertiesCSFW.pdf](https://www.cs.cornell.edu/fbs/publications/HyperpropertiesCSFW.pdf)
- "Refinement does not preserve hyperproperties" — a refinement of a secure specification may be insecure. [summary] — same source
- Goguen–Meseguer noninterference "requires that commands issued by users holding high clearances be removable without affecting observations of users holding low clearances." [summary] — search summary of the same paper
- Self-composition/product-program verification: k-safety reduces to ordinary safety of the k-fold product. [summary; the fetch paraphrased this as "any hyperproperty," which is too strong — the original claim is about k-safety] — same source; Barthe, D'Argenio, Rezk "Secure information flow by self-composition" (CSFW 2004) [memory]
- Boudol, "Secure Information Flow as a Safety Property" (FAST 2008): shows a per-program *safety* property that implies noninterference and can therefore be monitored. [memory; the Springer page required login] — [Springer](https://link.springer.com/chapter/10.1007/978-3-642-01465-9_2)
- "Differential privacy is a relational property of programs (also known as a hyperproperty)." [summary] — [Synthesizing Coupling Proofs of DP](https://par.nsf.gov/servlets/purl/10061759)
- NMIF is a 4-safety hyperproperty (needs four traces to witness a violation). [summary] — [arXiv 1708.08596](https://arxiv.org/pdf/1708.08596)

### Inferences
- For the reader's example-based specification: a *trace* example ("this command by this actor is refused") is a genuine spec of a safety property and can be checked on a recorded run. Confidentiality cannot be specified by one example; the minimal example is a *pair* of journeys differing only in private zone data with identical outside observations — a "two-run scenario." Property-based testing of noninterference does exactly this by generating pairs of low-equivalent states (Hritcu et al., "Testing Noninterference, Quickly," ICFP 2013 [memory]).
- Since refinement does not preserve hyperproperties, a noninterference theorem on the model does not transfer to an implementation by ordinary refinement; this is why Cedar pairs a proven model with differential testing of the implementation (Q4) and why the reader's "scrub round trip"/replay checks are complementary to, not substitutes for, a model theorem.

- Boudol's abstract was not readable (login redirect); the claim is from memory.

## Q4. Authorization as a verified model: Cedar's Lean theorems; actor checks and access-control models; authorization logic

### Takeaway
Cedar's Lean development proves forbid-overrides, default deny, explicit permit required, order/duplicate independence, sound policy slicing, sound validation (typechecking), sound level-based entity slicing, and sound-and-complete symbolic compilation and verification; the Lean model is the specification and the Rust implementation is checked against it by differential random testing. A command carrying an actor checked by a policy is a reference monitor; Cedar's request shape (principal, action, resource, context) covers RBAC, ABAC and ReBAC. Abadi showed DCC's monad reads as an authorization logic's `says`, so IFC and authorization share one calculus.

### Cited Findings
- cedar-lean README, proved properties (directory `Cedar/Thm/`): **Authorization** — forbid overrides ("If some forbid policy is satisfied, then the request is denied"), explicit permission required, default deny, order and duplicate independence; **Slicing** — sound policy slicing; **Typechecking** — "well-typed expressions either return values of that type or specific error types"; **Validation/Levels** — sound level-based entity slicing; **SymbolicCompilation** — "SMT terms both overapproximate and underapproximate expression semantics" (sound and complete) and compilation succeeds on well-typed expressions; **Verification** — sound and complete equivalence/implication checks. Dependencies: `batteries` and `doc-gen4`; not Mathlib. [summary] — [cedar-spec/cedar-lean](https://github.com/cedar-policy/cedar-spec/tree/main/cedar-lean)
- Cedar paper (OOPSLA 2024): "If any `forbid` policy evaluates to `true`, the request is denied"; "If no `permit` policy evaluates to `true`, the request is denied"; "If a request is allowed, some `permit` policy evaluated to `true`"; sound slicing; validation soundness: if the policy typechecks under entity type map M, evaluation produces a value (not an error) for all entity stores conforming to M. Requests are `principal`, `action`, `resource` (entities) and `context` (record). Cedar supports "role-based, attribute-based, and relation-based access control (RBAC, ABAC, and ReBAC)." The Lean spec is "executable by compilation to native code"; DRT with cargo-fuzz "uncovered nearly two dozen bugs." [summary] — [arXiv 2403.04651 (HTML)](https://arxiv.org/html/2403.04651)
- "How We Built Cedar" (FSE 2024): verification-guided development = executable Lean model + mechanized proofs, production Rust code checked by differential random testing, property-based tests for unmodeled parts; proofs found 4 validator bugs, DRT/PBT 21 more. [summary] — [ACM DL](https://dl.acm.org/doi/10.1145/3663529.3663854)
- NIST SP 800-162: ABAC is "a logical access control methodology where authorization to perform a set of operations is determined by evaluating attributes associated with the subject, object, requested operations, and, in some cases, environment conditions against policy." [summary] — [NIST SP 800-162](https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-162.pdf)
- Sandhu, Coyne, Feinstein, Youman, "Role-Based Access Control Models" (IEEE Computer 1996), the RBAC96 family of four models. [summary] — [ACM DL](https://dl.acm.org/doi/10.1109/2.485845)
- Capability-based access control: Dennis and Van Horn 1966; Miller, Yee, Shapiro "Capability Myths Demolished" 2003. [memory]
- Abadi, "Access Control in a Core Calculus of Dependency" (ENTCS 2007): DCC's type system "serves as an authorization logic, where instead of `T_L` one can read the type as `L says T`"; `A says s` means A has caused s to be said or supports s. [summary] — [abadi06.pdf](https://people.mpi-sws.org/~dg/teaching/lis2014/modules/authorization-3-abadi06.pdf)
- Flow-Limited Authorization (Arden, Liu, Myers, CSF 2015): IFC and authorization "can subvert each other's security"; FLAM integrates them, treating delegation/revocation and the flows created by authorization decisions themselves. [summary] — [eCommons](https://ecommons.cornell.edu/entities/publication/a0ee6cf5-6c73-4c53-9715-1203ad1ae1dd); calculus version CSF 2016 — [arXiv 2104.10379](https://arxiv.org/pdf/2104.10379)
- Reference monitor (Anderson 1972) and complete mediation (Saltzer and Schroeder 1975), as in Q0. [summary]

### Inferences
- The reader's "commands carry an actor that a policy checks before a decision" is a reference monitor at the command boundary. The theorem it should carry, in Cedar's shape: (i) *explicit permit*: every `Decision` has a policy-satisfying actor; (ii) *default deny*: a command whose actor satisfies no rule yields no decision; (iii) *determinism/order independence* if the policy is a set of rules. In Lean, (i) is free if `Decision` is only constructible from a proof of `allows`, and (ii)–(iii) are small lemmas about the policy evaluator.
- FLAM is the reference for why the actor check and the zone indices must be reasoned about together: the authorization result itself is information (the refusal reveals something about policy and data), so the policy decision needs a zone label, and policy *changes* are flows.
- Abadi's reading `T_L A` = "L says A" suggests a direct encoding in the reader's model: a value of type `Id z` is "zone z says this identifier is valid," and a `Decision` built from `allows actor cmd` is "policy says actor may cmd."

## Q5. Differential privacy as a quantitative privacy attribute; SampCert; is DP a hyperproperty; verified-DP lineage

### Takeaway
(ε,δ)-DP bounds how much any one individual's presence can shift an output distribution; it is a relational (hyper)property over distributions, not a trace property. The lineage of mechanized DP runs CertiPriv (Coq, POPL 2012) → apRHL/couplings (Barthe et al.) → Fuzz-style sensitivity types (Reed and Pierce) → SampCert (Lean 4 + Mathlib, >12,000 lines, generic over pure/concentrated/Rényi DP, discrete Laplace and Gaussian samplers, deployed at AWS) and an Isabelle/HOL formalization (2024) supporting continuous distributions.

### Cited Findings
- Definition: a randomized mechanism M is (ε,δ)-DP if for all adjacent inputs D, D′ (differing in one record) and all output sets S, Pr[M(D)∈S] ≤ e^ε·Pr[M(D′)∈S] + δ (Dwork, McSherry, Nissim, Smith 2006). [memory]
- SampCert, "Verified Foundations for Differential Privacy" (de Medeiros, Naveed, Lepoint, Kahsai, Ravitch, Zetzsche, Joshi, Tassarotti, Albarghouthi, Tristan; arXiv Dec 2024, rev. Apr 2025): "a generic DP foundation that can be instantiated for various DP definitions (e.g., pure, concentrated, Rényi DP)"; "formally verified discrete Laplace and Gaussian sampling algorithms"; "a simple probability monad and novel proof techniques"; "makes heavy use of Lean's extensive Mathlib library, leveraging theorems in Fourier analysis, measure and probability theory, number theory, and topology"; "over 12,000 lines of proof"; the verified algorithms "power the DP offerings of Amazon Web Services." [summary] — [arXiv 2412.01671](https://arxiv.org/abs/2412.01671)
- SampCert repository: zCDP based on Bun–Steinke; discrete Gaussian sampler per Canonne–Kamath–Steinke; "some unbounded private queries"; uses the Poisson summation formula from Mathlib; "deployed and used in the AWS Clean Rooms Differential Privacy service." [summary] — [leanprover/SampCert](https://github.com/leanprover/SampCert)
- CertiPriv (Barthe, Köpf, Olmedo, Zanella Béguelin, POPL 2012): "a machine-checked framework for reasoning about differential privacy built on top of the Coq proof assistant," a quantitative extension of probabilistic relational Hoare logic (apRHL), with "the first machine-checked proofs of correctness of the Laplacian, Gaussian, and exponential mechanisms." [summary] — [Zanella.2012.POPL.pdf](https://software.imdea.org/~szanella/Zanella.2012.POPL.pdf)
- Barthe et al., "Proving Differential Privacy via Probabilistic Couplings" (LICS 2016) and "Advanced Probabilistic Couplings for DP" (CCS 2016): approximate couplings as the proof abstraction in apRHL; "clean, compositional proofs for many examples beyond the reach of the standard composition theorems." [summary] — [arXiv 1601.05047](https://arxiv.org/pdf/1601.05047); [arXiv 1606.07143](https://arxiv.org/pdf/1606.07143)
- Reed and Pierce, Fuzz (ICFP 2010): a linear-like type system in which "the type system captures function sensitivity ... well-typed programs ... can't go too far on nearby inputs," and with a monad for random computations "the established definition of differential privacy falls out naturally as a special case of this soundness principle." [summary] — [dp.pdf](https://www.cis.upenn.edu/~bcpierce/papers/dp.pdf)
- Sato and Minamide, "Formalization of Differential Privacy in Isabelle/HOL" (arXiv Oct 2024): standard definition and basic properties, Laplace mechanism, report noisy max; "the first formalization of differential privacy that supports continuous probability distributions." [summary] — [arXiv 2410.15386](https://arxiv.org/abs/2410.15386)
- DP "is a relational property of programs (also known as a hyperproperty)." [summary] — [NSF PAR](https://par.nsf.gov/servlets/purl/10061759)

### Inferences
- DP is a hyperproperty in the sense that it relates two executions (adjacent inputs), but it is a bound on *distributions*, so no finite set of traces witnesses a violation; it is not k-safety in Clarkson–Schneider's sense. This matters for the reader: DP cannot be checked on recorded runs at all, only proved about the mechanism (SampCert) or estimated statistically.
- SampCert is the right dependency if the reader ever releases *statistics* across zones: its abstract DP interface is a Lean 4 library with Mathlib, so a `scrub`-like release of aggregates could be typed as a DP mechanism with an ε budget, making privacy a quantitative attribute of the function. Cedar, by contrast, uses only Batteries, so the two verified libraries sit at different weights.
- Fuzz is the type-system analogue for DP of what VSI is for noninterference: sensitivity in the type, DP as the soundness theorem.

### Gaps
- Exact SampCert theorem names and whether approximate (ε,δ)-DP is instantiated (vs pure and zCDP) were not confirmed in the source.

## Q6. Privacy by construction in data architectures: pseudonymization with a key held in one place; formal treatments; GDPR

### Takeaway
GDPR Article 4(5) defines pseudonymisation as processing such that data "can no longer be attributed to a specific data subject without the use of additional information," with that information "kept separately" under technical and organisational measures — a legal statement of the reader's private-zone-plus-scrub design. ENISA's 2019 report is the engineering reference. No proof-assistant formalization of pseudonymization or k-anonymity was found; the formal analogues are declassification (cryptographically masked flows) and DP.

### Cited Findings
- GDPR Art. 4(5), verbatim: pseudonymisation is "the processing of personal data in such a manner that the personal data can no longer be attributed to a specific data subject without the use of additional information, provided that such additional information is kept separately and is subject to technical and organisational measures to ensure that the personal data are not attributed to an identified or identifiable natural person." Art. 4(1): personal data is "any information relating to an identified or identifiable natural person." [source, via fetch] — [gdpr-info.eu Art. 4](https://gdpr-info.eu/art-4-gdpr/)
- Recital 26: pseudonymised data remain personal data; anonymous data are outside the Regulation. Art. 25 names pseudonymisation as an example data-protection-by-design measure; Art. 32 lists it as a security measure. [memory]
- ICO: a key "exists — the mapping between the original identifiers and the artificial references is maintained, and re-identification is possible for anyone who has access to this key"; pseudonymisation "is only effective if the key and the pseudonymised data are stored separately and the key is adequately protected." [summary] — [ICO pseudonymisation guidance](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-sharing/anonymisation/pseudonymisation/)
- ENISA, "Pseudonymisation Techniques and Best Practices" (Nov 2019): parameters are "data protection, utility, scalability and recovery"; "there is no single easy solution to pseudonymisation that works for all approaches in all possible scenarios"; use cases for IP addresses, email addresses, complex data sets. [summary] — [ENISA news](https://www.enisa.europa.eu/news/enisa-news/enisa-proposes-best-practices-and-techniques-for-pseudonymisation)
- Static (persistent) tokens are criticised for enabling linkage ("mosaic effect") attacks; dynamic pseudonyms are proposed instead. [summary; source is a vendor/patent-adjacent page] — search summary
- k-anonymity: a release is k-anonymous if every quasi-identifier combination appears at least k times (Sweeney 2002); l-diversity and t-closeness refine it. [memory]
- The Isabelle/HOL DP formalization is the closest proof-assistant work to anonymization found. [summary] — [arXiv 2410.15386](https://arxiv.org/abs/2410.15386)

### Inferences
- The reader's scrub with the re-identification key in the private zone is Art. 4(5) in types: "additional information kept separately" = the key lives only in the private zone and no function other than `scrub` names both zones. The formal property to state is cryptographically-masked-flows-style noninterference: the outside zone's observations are unchanged under any permutation of private zone identities consistent with the pseudonym map.
- The "static token" criticism is a design risk: if `scrub` is deterministic, equality of pseudonyms across records is itself a flow (linkage); the delimited-release hatch then releases "the equality relation on identities," which should be acknowledged in the spec or avoided by per-context pseudonyms.

### Gaps
- No formalization of GDPR pseudonymisation, k-anonymity, or l-diversity in Coq/Isabelle/Lean was found this session.
- Recital/article numbers for data-protection-by-design (Art. 25) and security (Art. 32) are from memory.

## Q7. Security requirements as examples: misuse/abuse cases, security Gherkin, and whether a negative example is a well-formed spec-by-example

### Takeaway
Misuse cases (Sindre and Opdahl; Alexander) are the standard way to write security requirements as negative scenarios with *threatens/mitigates* links to use cases; BDD-Security and Gauntlt write them as Gherkin. A "must refuse" example is a well-formed spec-by-example because it states a safety (trace) property and is checked on one run; a confidentiality example is not, because noninterference is 2-safety and needs a pair of runs.

### Cited Findings
- Sindre and Opdahl: a misuse case is "the inverse of a use case, i.e., a function that the system should not allow ... a completed sequence of actions which results in loss for the organization or some specific stakeholder"; they propose five steps (identify assets, security goals, threats, risks, requirements) and stereotypes "prevents" and "detects." [summary] — [RIT SE555 notes](https://www.se.rit.edu/~se555/Misuse%20Cases.pdf); [Requirements Engineering 2005](https://link.springer.com/article/10.1007/s00766-004-0194-4)
- Wikipedia: misuse cases introduce *threatens* and *mitigates* relations; Alexander's IEEE Software 2003 article popularised them; abuse cases (McDermott and Fox 1999) are the precursor. [summary] — [Wikipedia: Misuse case](https://en.wikipedia.org/wiki/Misuse_case)
- BDD-Security (IriusRisk, formerly Continuum Security; Stephen de Vries [memory]): "a security testing framework that uses Behaviour Driven Development concepts to create self-verifying security specifications," Cucumber-JVM/Gherkin, driving OWASP ZAP, SSLyze, Nessus and Selenium; "tests Web Applications and API's from an external point of view"; AGPL-3.0. [summary] — [iriusrisk/bdd-security](https://github.com/iriusrisk/bdd-security)
- Gauntlt: "a ruggedization framework ... usable by devs, ops and security"; attack files are Gherkin with a `.attack` extension, built on Cucumber, driving curl, nmap, sslyze, sqlmap, Arachni. [summary] — [gauntlt/gauntlt](https://github.com/gauntlt/gauntlt)
- BehaveSafe: a method for defining security and privacy acceptance criteria in BDD via a threat-and-countermeasure graph. [summary] — [Springer](https://link.springer.com/chapter/10.1007/978-3-319-13835-0_28)
- Cedar's differential random testing is example-based checking of an implementation against a proven model: "nearly two dozen bugs" found by cargo-fuzz DRT. [summary] — [arXiv 2403.04651](https://arxiv.org/html/2403.04651)
- Property-based testing of noninterference generates pairs of low-equivalent states (Hritcu et al., ICFP 2013). [memory]

### Inferences
- A negative example "Given actor X, When command C, Then refused" is well-formed: it is one trace, the predicate is decidable on it, and it is exactly a misuse case with its mitigation. It specifies the *authorization* attribute (a safety property) and matches Cedar-style theorems (default deny, forbid overrides).
- A confidentiality example must be written as a pair: "Given two private zone states differing only in identity, When the same journey runs, Then the outside-zone observations are equal." This is the minimal faithful spec-by-example for noninterference, and it is what a generated pair-test checks; a single "the id is not shown" scenario is only a symptom check.
- For the reader's trace predicates ("promises as trace predicates"), authorization promises are first-order over one trace; confidentiality promises are second-order over trace pairs; DP promises are over distributions and cannot be stated as examples at all.

### Gaps
- Sindre and Opdahl's 2005 journal text was behind a login; the definition is from a secondary summary.
- Stephen de Vries's authorship of BDD-Security is from memory.

## Q8. Next steps for the reader's Lean 4 model (synthesis)

### Takeaway
State the three attributes as three theorems of different shape, prove the two that are provable now, and write the examples in the shape the theorems dictate.

### Cited Findings
- Model-as-specification with proofs plus differential testing of production code is the published Cedar method. [summary] — [FSE 2024](https://dl.acm.org/doi/10.1145/3663529.3663854)
- Binary logical relations are the standard mechanized route to noninterference for typed languages with state. [summary] — [Gregersen et al. POPL 2021](https://pure.au.dk/portal/en/publications/mechanized-logical-relations-for-termination-insensitive-noninter/)
- Iris is now available in Lean 4 with Mathlib. [summary] — [arXiv 2609.24252](https://arxiv.org/abs/2609.24252)
- SampCert provides a generic DP foundation in Lean 4 over Mathlib. [summary] — [arXiv 2412.01671](https://arxiv.org/abs/2412.01671)

### Inferences
1. **Authorization (safety, one run).** Make `Decision` constructible only from `Policy.allows actor cmd` evidence, then prove Cedar's trio: explicit permit, default deny, order independence of the rule set. Write the misuse cases as single-run Gherkin examples and run them as DRT against any implementation.
2. **Confidentiality (2-safety, two runs).** Give the model's commands an explicit small-step or big-step semantics in Lean and prove: for all states `s₁ ≈_A s₂` (equal on zone A observables), and every well-formed command, results are `≈_A`. The zone index on `Id` is used as the definition of `≈_A`, not as the proof. Then state `scrub`'s delimited release: add `scrub` outputs to the equivalence and re-prove. Write the two-run example as a generated pair-test.
3. **Who (robustness).** Require private-zone-integrity `pc` at the `scrub` call: prove that no command whose actor is outside the private zone's trust can reach `scrub` (a one-run safety lemma, since the actor check is a reference monitor), which, with 2, yields robust declassification.
4. **Pseudonym quality.** State the cryptographically-masked-flows condition for `scrub` (output invariant under identity permutations fixing the pseudonym map) and decide whether pseudonym equality across records is a declared hatch.
5. **Privacy as a number** only if aggregates leave the private zone: type that release as a SampCert mechanism with a budget.

### Gaps
- Whether Lean 4's `Type` supports a parametricity-style "free" noninterference argument is not settled in anything found; the safe route is the explicit two-run theorem.
